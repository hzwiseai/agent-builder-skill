# 对客话术设计规范

这一份讲的是**一句话怎么写**，跟改在哪一层无关。组织岗位和平台模板共用同一套
判断——`skills/sales-flow-designer/references/script-design.md` 是系统侧的同源
文档，两边内容有出入时以运行时消费的实际位置为准（见本页最后一节）。

配置块（`units`、`conversion_checkpoint`、`cadence` 等六块）怎么填在
[渐进说明技能](sales-progressive-explanation.md)；这里只管对客文本本身。

## 目标

让客户获得有用信息、判断是否适合、自主选择下一步。注册、购买、预约、留资是
不同的转化目标，动手前先定一个；纯客服以解决问题为完成，不强加转化。

## 七阶段：设计与评审框架，不是状态、不是固定轮次

| 阶段 | 客户心里在问 | 本阶段必须提供 | 可推进的信号 |
| --- | --- | --- | --- |
| 开场 | 你是谁、找我什么事 | 身份 + 相关来意；入站先回应原问题 | 客户提问或愿意继续 |
| 建立信任 | 你理解我吗、可信吗 | 准确理解、可核实信息、诚实边界 | 客户开始谈实际问题 |
| 了解需求 | 你能解决我哪件事 | 梳理现状与目标，解释问题用途 | 已知足以推荐 |
| 介绍方案 | 对我有什么用、怎么实现 | 一项相关价值、机制、适用条件、证据 | 客户理解适用性或转入疑虑 |
| 处理异议 | 太贵/麻烦/不可信怎么办 | 回答真实顾虑、核实、可行选择 | 客户确认顾虑已回应 |
| 促进成交 | 下一步做什么、成本责任 | 清楚动作、目的、条件，允许拒绝 | 客户明确选择 |
| 保持关系 | 之后找谁、还会打扰我吗 | 有用支持、约定跟进、清楚承接 | 解决 / 同意安排 / 明确结束 |

跨阶段：主动问价先答价；主动要入口直接给核实过的入口；异议暂停推进先回应；
换需求重选方案；明确拒绝停止。多轮不重复开场，不让客户重给已有信息。

**「我已经解释过」不等于顾虑已解决。** 发过话术不是信号，客户的回应才是。

## 每轮结构：承接 → 信息 → 至多一个问题

- 承接具体内容，不靠「好的/理解/没问题」占一句；不每轮复述客户行业。
- 先答已问的；答案依赖某个条件时先解释原因，再只澄清这一项。
- 默认两三句，一轮一个主信息点；客户要对比或步骤时才展开。
- 一次最多一个必要追问。一条消息带多项信息就一起承接，**已知的不再问**。
- **去问句测试**：删掉末尾问句，剩下的回答仍应有价值。不要用「您觉得呢」
  「需要了解更多吗」当固定结尾。
- 不向客户念内部概念：阶段名、FABE、事实 key、待追问、工具回执。
- 不恐吓、不羞辱、不虚假稀缺、不虚构背书。

篇幅约束要写成可判定的数字（单句多少字、整条几句），但**涉及否定、边界和
不承诺的句子不受字数限制**——「不便直接发送」「不报价」「不承诺时间」这类话
压缩后一旦丢掉否定词，意思会反过来变成承诺。宁可多一句。

## 了解需求：为了推荐而问

按缺项选问题，不机械执行问卷。够用就推荐；预算、人数、联系方式不是统一必问。
客户不知道或不愿答时，用已有信息给一般建议并标明适用限制。问影响用中性问法。

## 介绍方案：需求驱动的 FABE

F 特征（具体能做什么，已核实）→ A 优势（怎样改善，说机制与条件）→
B 利益（对这位客户的帮助，未验证效果用条件式）→ E 证据（案例/演示/文档，
说明各自的证明范围）。

四项是**完整性检查**，不要求按字母顺序输出。对客顺序通常是
**B → F/A → 与当前疑虑相关的 E**。客户只问一个功能就只答 F + 适用条件；
怀疑效果再补 E。

多方案：先按需求筛选再比较少数选项；公共内容不重复，不同方案的价格与证据
不混用；换场景重新判断，**不把旧方案的认可当作对新方案的同意**。

## 处理异议：四段式，顺序不能换

**承接顾虑 → 必要时澄清一个问题 → 针对性回应与证据 → 确认方向或等待**。
根因已经清楚就直接答。「多少钱」是咨询，「太贵不值」才是异议。

| 异议 | 必要时了解 | 回应重点 | 不能 |
| --- | --- | --- | --- |
| 太贵 | 预算/投入/收益不明？ | 已知价格范围、包含内容、允许不适合 | 擅自打折、编造回报 |
| 担心效果 | 哪类场景、之前哪里没达到？ | 相似证据、限制、可验证的试用 | 保证某个案例数字 |
| 实施麻烦 | 资料/接入/人员？ | 真实准备项与人工边界 | 「零配置当天上线」 |
| 已有产品 | 哪点已满足、哪点未满足？ | 承认已有价值，只比有证据的差异 | 贬低竞品、重推同一方案 |
| 暂不需要 | 时机还是适用性？ | 允许暂停；有价值且获同意再约 | 连续挽回、换说法催 |
| 安全/数据 | 具体关心什么 | 引用实际政策，必要时由有权限的人确认 | 「绝对安全」 |
| 明确拒绝 | 不再追问 | 简短确认，停止推进与触达 | 当成待攻克的异议 |

每条异议要填满一行才算设计完：触发原话（≥3 种变体）与易混淆点 / 回应原则 /
话术 / **怎样算已解决** / 下一步（恢复哪些内容、等待、还是停止）/ 不能说。

处理完只恢复仍然相关的内容，不重头开场，不清空已收集的信息。

## 促进成交：邀请明确动作，不推断同意

| 转化目标 | 必须说清 |
| --- | --- |
| 注册体验 | 目的、真实入口、必要条件 |
| 预约演示 | 目的、所需联系信息、明确时间 |
| 留资 | 留什么、为什么、后续谁做什么 |
| 购买 | 选择内容、价格与关键条款，按实际权限执行 |

「好」「知道了」**不是授权**；只有结合最近一次实际邀请的明确答应才能采纳。
愿意了解 / 愿意体验 / 已注册 / 已购买 / 已预约要分别判断。客户直接索要入口
时无需走完介绍。时间按可靠的当前时间和业务时区建议，仍需客户确认。

**只有能力返回成功回执之后才可以说「已安排」「已登记」「已同步给销售」。**
把没发生的事说成已发生，客户据此等待，而承接方那边什么都没有。

## 保持关系

成交或注册后先回应当前问题，不立即追加推销。后续联系每次都要有明确价值，
不用「在吗」「考虑得怎么样」催。没有交接回执就不说「销售会马上联系」。

## 一条话术进库前的六要素

名称（业务人能懂、客户问题明确）/ 适用阶段与目标 / 客户触发（原话、以及
不适用的情况）/ 已知信息前提 / 事实与证据来源 / 核心信息（客户听完理解什么）/
正文（能自然说出口，无占位符）/ 下一步 / 变化分支（拒绝、换需求、无证据、
执行失败）/ 禁止事项 / 验证例（适用、不适用、中断各一条）。

**三一致**：名称、描述、正文对应同一个问题。描述写「什么时候用、什么时候
不用」，不共用免责声明。正文不要固化末尾追问。合规内容也要说人话。

## 口吻和人设写在哪：写进 policies，不要写进 `expression.voice`

这一条与系统侧文档不同，以运行时为准。发布预检的消费矩阵对 `expression.voice`
的判定是：

> Tone and persona written here never reach the decision.
> **Put required speaking behaviour in policies.**

它既没有 `decision_consumer` 也没有 `execution_consumer`，写在那里的语气、
人设和篇幅约束**一个字都到不了模型**。发布预检会以
`v2_consumption_matrix_expression_field_not_consumed:<包>:voice` 报 warning，
但预检仍然 `ready`——所以它只会被忽略，不会拦住你。

现实里踩过的样子：某岗位的 `voice.example` 写着一次问清多个字段，`voice.tone`
同时写着「一次只推进一步」，两者自相矛盾且都不生效，真正生效的是
`policies` 里那条同样写着「一次只推进一步」的。改了 example 半天没有反应。

所以：**说话方式要生效，就写成 policy 语句**。`expression.voice` 可以留作
给维护者看的注释，但不要指望它改变行为，也不要只改它就认为改完了。

## 各项设计内容的落点

| 设计内容 | 位置 |
| --- | --- |
| 语气、人设、篇幅限制 | **岗位 `policies`**（不是 `expression.voice`） |
| 需求了解、多方案适用 | `skill_configuration` 的 `discovery_topics` / `solution_tracks` |
| 客户问题、必讲的意思 | `skill_configuration.units` |
| 异议触发/回应/怎样算解决/恢复 | `objection_handlers` + 政策 |
| 何时邀请、需要什么明确选择 | `conversion_checkpoint` |
| 具体措辞 | 话术条目 + `expression.recall_bindings` |
| 事实、案例、实时数据 | 知识中心 / 案例查询 / Capability |
| 跨轮信息与进度 | 已声明的 Fact |
| 预约、人工承接 | 已安装的任务 + `journey_handoffs` |
| 未回复跟进 | `cadence` |

## 交付前自检（任一不过就不要发布）

- [ ] 无虚构的价格、功能、案例、数字、优惠期限、成功回执
- [ ] 客户的业务目标没有被当成购买、联系或预约的授权
- [ ] 明确拒绝后停止；无恐吓、虚假稀缺、反复追问
- [ ] 占位符和内部术语没有进入对客内容
- [ ] 否定句和边界句没有因为篇幅压缩而丢掉否定词

## 最小回放集（13 条）

模糊场景只补必要信息 / 首轮问价先答价 / 一句多项需求一起承接 /
已知需求后介绍不背目录 / 中途换产品重选方案 / 「太贵」原因明确时直接回应 /
案例未命中如实说明 / 介绍后「好的」不记为同意 / 索要入口直接给 /
演示只说「现在」时给建议并等确认 / 已注册的人提问不重复引导 /
暂缓时感谢并按意图停止 / 执行失败不说成功。

优化已有话术时的交付格式：原文与问题 → 优化后 → 修改理由 → 适用条件与依据 →
待补材料。保留已核实的数字；发现口径冲突时指出并等待核实，**不要自己挑一个
更好卖的说法**。
