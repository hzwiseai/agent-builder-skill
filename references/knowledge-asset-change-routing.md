# 知识与资产变更分流规范

## 权威关系

知识中心是业务事实的权威来源；岗位、任务和 Agent 资产是行为规则与执行边界的承载层。知识发布不会隐式修改资产，资产保存也不会隐式覆盖知识中心。

## 先分类，再动手

| 变更类型 | 典型内容 | 首选动作 |
| --- | --- | --- |
| 知识-only | 薪资、地址、产品参数、注册步骤、FAQ答案、资料链接 | 修改知识条目，审核并发布知识版本；若条目声明了 asset compile target，再执行独立编译 |
| 资产-only | 岗位/任务路由、Fact 收集、Guard、能力绑定、状态迁移、回复选择、Eval | 修改对应 V2 资产并补 Eval；不改知识中心 |
| 知识+资产 | 新增一个业务事实且需要模型在特定阶段主动询问/阻断/调用工具 | 先补知识条目，再修改资产承载行为，最后用同一需求做闭环验证 |
| 责任面外 | 回复模板库、系统基础资产、渠道或账号绑定 | 生成 finding，转到对应责任面；禁止用知识条目或业务政策伪装修复 |

判断标准不是“文字像不像知识”，而是：改变的是可核验事实，还是模型的行为决策/执行边界。薪资数字属于知识；“何时询问薪资、是否允许预约”属于资产。

## 知识改动后的闭环

1. 修改、审核并发布知识条目，得到新的 knowledge release。
2. 读取 `design_get_knowledge_compile_input`，只对声明了精确 `asset_ref` 和适用岗位的条目生成资产候选。
3. 对照当前资产生成 bounded diff；通过候选验证后，用户确认才写入岗位/任务草稿。
4. 重新预检并发布业务包；发布后回放相关 Eval/Trace，确认事实和行为都已生效。

## 资产改动如何更新回去

资产不是知识源，不能把整个资产文档反向上传覆盖知识空间。若资产改动中出现新的业务事实（例如新增价格、流程、承诺或资格条件）：

1. 生成“知识回填提案”，保留原资产字段、变更前后值、来源资产版本和适用岗位。
2. 在知识空间中创建/修订对应知识条目，标注来源为资产变更提案；走正常审核和发布。
3. 发布后重新读取编译输入，确认知识条目与资产字段一致；不一致时报告冲突，不自动覆盖任一侧。

如果资产改动只是路由、Guard、Fact 依赖、能力绑定或表达策略，不产生知识回填提案，只需资产 Eval 和运行验证。

## 冲突与并发

- 知识发布和资产发布分别使用各自的版本/基线锁；任一侧发生 stale 都要重新读取、重做 diff，不允许静默覆盖。
- 反向回填必须引用具体资产版本和字段，不能从模型记忆或整段文档猜测事实。
- 资产与知识同时变更时，保留两条审计链：knowledge release → compile proposal → asset draft/release，以及 asset change → knowledge backfill proposal。
